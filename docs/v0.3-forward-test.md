# Designome v0.3 prompt forward test

Date: 2026-09-01

## Objective

Verify that the v0.3 prompt and contract set extracts a deeper, explicitly bounded UI grammar from known dashboard references, routes selected captures by subject, and refuses unsupported destination-specific fidelity.

This is a prompt-contract forward test, not a browser or usability test. The two source images were inspected locally and were not copied into the repository.

## References

- Reference A: a large desktop analytics dashboard with persistent navigation, filters, KPI summaries, comparison values, chart cards, legends, setup progress, and a data table.
- Reference B: a desktop platform dashboard with French content, persistent navigation, a period selector, KPI cards, zero/empty states, percentages, and sparklines.

Both references visibly establish dashboard/web-application evidence. Neither establishes a corporate marketing website or mobile-native application.

## Scenarios

### 1. Open evidence routing

The deterministic initializer accepted both image formats and produced:

- run-plan schema `0.2.0`;
- 18 prompt stages;
- 13 axis stages;
- routing status `awaiting-source-evidence`.

This is the expected state for unrestricted sources: the runtime cannot perform visual classification, so the host source-evidence stage must admit visible regions before specialist execution.

### 2. Per-source subject routing

The runtime test suite normalized an `only` directive for a statistics capture with:

- `axis.data-display-visualization`;
- `domain.stats-kpis`.

The run plan enabled the axes connected to the KPI domain plus required system governance, retained all five facet IDs for the data specialist, and skipped an unrelated spatial axis when no open visual routing remained. Semantic Design DNA validation also rejected:

- a token claim that used evidence outside a source's `only` directive;
- a token claim that used evidence for a domain explicitly excluded by its source.

This proves that conversational routing survives normalization, planning, synthesis validation, and installation documentation rather than existing only in prompt prose.

### 3. Deep dashboard extraction

The v0.3 axis/domain contracts surfaced the following admissible grammar:

| Area                         | Evidence-supported result                                                                                                                                                              | Preserved limit                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Spatial composition          | Persistent rail/canvas separation, repeated card tracks, nested data regions, stable alignment anchors                                                                                 | Exact grid values, scroll ownership, and breakpoints remain unknown                                  |
| Typography/content hierarchy | Distinct navigation, section, label, primary-value, unit, comparison, and supporting-text roles                                                                                        | Font identity and exact sizes are not claimed                                                        |
| Color/surface/identity       | Restrained nested surfaces, subtle borders, blue accent, semantic data colors, quiet icon containers                                                                                   | Exact production values and universal semantic meaning remain unclaimed                              |
| Component morphology         | Metric cards, chart cards, rows, filters, segmented controls, badges, and setup progress have separable anatomy                                                                        | Unseen variants and interactive behavior are proposed or unknown                                     |
| Navigation/task architecture | Persistent orientation, grouped destinations, current location, global period control, and local drill-down cues                                                                       | Destination behavior and complete product architecture are not visible                               |
| Data display                 | KPI label/value/unit/context, timeframe, comparison baseline, trend direction, chart encoding, legend, precision, empty/zero data, and mini-trend treatment are separately inspectable | Formula, freshness, desirability, uncertainty, tooltip behavior, and data correctness remain unknown |
| Content/localization         | French labels in Reference B exercise content length and numeric punctuation independently of Reference A                                                                              | One locale does not establish full translation or bidirectionality                                   |
| States/resilience            | Visible zero/empty representations and setup progress are observed; loading, failure, stale, permission, and recovery states are explicit gaps                                         | Static frames do not prove transitions or async behavior                                             |

The dedicated statistics/KPI contract was materially useful. It prevented a metric card from being reduced to “large number in a card” by requiring label, value, unit, comparison, timeframe, target, freshness, precision, desirability, zero/missing/stale behavior, and drill-down context to be considered independently.

The chart contract similarly separated encoding, scale, axes, legend, labels, annotations, interaction, uncertainty, and accessible alternatives. Visible dot/hex and sparkline treatments did not authorize reconstruction of source data or interaction behavior.

### 4. Coverage honesty

The schema-valid v0.3 reference contains:

- 13 axis records;
- 65 facet records;
- 20 UI-domain records;
- typed source classification and directives;
- typed tokens, rules, and component contracts.

For these static desktop references, forms, most interaction states, responsive behavior, mobile-native behavior, implemented accessibility semantics, measured performance, and runtime recovery remain mostly `unknown`. Their presence in the coverage ledger is not status inflation; it makes missing proof reviewable.

### 5. Destination mismatch

The compatibility contract produced the following required decisions:

- Direct corporate-site fidelity: unsupported without representative corporate/marketing website captures. Dashboard references may contribute only admitted subjects such as KPI, chart, typography, color, or surface grammar.
- Direct mobile-app fidelity: unsupported without representative mobile-app captures and visible platform evidence. Narrow dimensions alone would not prove native mobile.
- Explicit adaptation: allowed, but corporate or mobile patterns absent from the references remain `proposed` and require a forward test.
- Meaningless optional text: recorded under ignored fragments and never converted into a destination or permission.

### 6. Installed projection

The installation tests rendered the accepted v0.3 grammar into 52 checksum-managed documentation files:

- 7 foundations;
- 6 component contracts;
- 20 UI-domain patterns;
- 11 behavior documents;
- 7 governance documents;
- one index.

The forward-test-critical outputs include:

- `patterns/stats-and-kpis.md`;
- `patterns/charts-and-data-visualization.md`;
- `components/variants-and-density.md`;
- `components/composition-and-anti-patterns.md`;
- `governance/source-routing.md`;
- `governance/coverage.md`.

Every projected document has an explicit epistemic boundary even when no accepted artifact covers the subject.

## Result

The v0.3 contract passed this forward test for depth, source isolation, destination compatibility, and coverage honesty. It is suitable for promotion as a contract/schema/prompt release.

## Limits and next validation

- No live application, interaction, keyboard, assistive-technology, responsive, performance, or motion execution occurred.
- The reference Design DNA remains `draft`; this test does not substitute for human acceptance.
- Corporate and mobile destination families still require matching references for direct fidelity.
- A later product-quality evaluation should generate a novel screen from accepted v0.3 DNA and run the four-layer audit against real browser evidence.
